# Архитектура

## Кто кого зовёт

Ключевое решение: **инициатор всегда DM**. Игра сама делает запрос и
получает моторную команду в теле ответа. Один round-trip на тик, никакого
входящего соединения в BYOND для основного цикла не нужно.

```
тик N   SSflybrain.fire()
          ├─ забрать ответ на запрос тика N-1  ──► apply_action()
          └─ собрать сенсорику, отправить запрос тика N
тик N+1 …
```

Муха живёт с задержкой ровно в один сенсорный тик — 200 мс по умолчанию.
Для мухи это щедро: её собственная зрительно-моторная петля работает за
30–60 мс, но персонаж в SS13 всё равно не ходит быстрее пары шагов в секунду.

## Транспорты

### `rustg` — рекомендуемый

`call(RUST_G, "http_request_async")` отдаёт запрос в фоновый поток Rust и
сразу возвращает хэндл. На следующем тике `http_check_request` либо
отвечает пустой строкой (ещё летит), либо отдаёт готовый JSON. DM не спит
ни на одном из этих вызовов — это несколько микросекунд на `call()`.

Библиотека берётся из релизов [tgstation/rust-g](https://github.com/tgstation/rust-g).
Своей копии `rust_g.dm` в TauCetiClassic нет, поэтому в модуле лежит
минимальная привязка только к HTTP-модулю; если полноценный `rust_g.dm`
когда-нибудь приедет в репозиторий, файл `rust_g.dm` из модуля просто
удаляется, имена совместимы.

### `file` — запасной, без бинарников

DM пишет пакет в `data/flybrain/<id>.in`, зовёт
`world.ext_python("flybrain_client.py", …)` и на следующих тиках проверяет
`fexists()` выходного файла. Клиент — тонкий скрипт на стандартной
библиотеке: он **не поднимает мозг заново**, а просто POST-ит пакет в тот
же самый работающий демон и кладёт ответ рядом. Загрузка коннектома
происходит один раз за жизнь демона, а не на каждый тик.

Стоимость: `shell()` порождает процесс, а `world.ext_python` усыпляет
вызывающую процедуру. Вызов завёрнут в `spawn(0)`, поэтому мир продолжает
тикать, но 50–200 мс на обмен остаются. Реалистичный потолок — 2–5 Гц.

Запись ответа атомарная (`os.replace`), так что DM не может прочитать
половину файла.

### Почему не `world.Export()`

Он умеет только GET и только синхронно. Сенсорный пакет — около килобайта,
в URL такое не запихнёшь, а синхронный вызов на каждый тик сажает мир.
Для редких внеполосных команд он годится, для основного цикла нет.

### Обратный канал `world/Topic()`

Python → сервер, для команд «заспавни муху», «дай статус», «отцепи».
Реализован в `topic.dm`, клиент протокола — в `flybrain/byond.py`
(BYOND-овый topic это не HTTP, а свой бинарный формат поверх TCP; в
`byond.py` он разобран по байтам). Требует трёх строк в `code/game/world.dm`,
см. `dm/world.dm.patch`. Без этой правки всё остальное работает.

## Формат пакета

Сенсорика — JSON. Поля зрения упакованы в строки: один символ `'0'`–`'9'`
на клетку вместо числа с плавающей точкой. 225 клеток превращаются в 225
байт, весь пакет укладывается примерно в килобайт вместо полутора.
Для файлового транспорта это принципиально: пакет проезжает через шелл.

```json
{
  "mob": "fly_1", "secret": "…", "tick": 412,
  "view_w": 15, "view_h": 15,
  "light": "3345566…", "solid": "0001100…",
  "mobs":  "0000000…", "items": "0000000…",
  "health": 0.94, "pain": 0.0, "hunger": 0.62,
  "temp": 293.1, "pressure": 101.3, "co2": 0.02, "toxin": 0.0,
  "food_near": 0.43, "food_touch": 0, "bitter": 0.0,
  "wind": 0.0, "sound": 0.0, "contact": 0.0,
  "on_fire": 0, "stunned": 0
}
```

Ответ:

```json
{
  "seq": 412, "dir": 4, "move": 1, "run": 1, "act": null,
  "dbg": {"state": "forward", "heading": 87.4, "turn": 0.31, "arousal": 0.12,
          "z": {"forward": 0.9, "escape": -0.2, …},
          "hz": {"forward": 118.8, …}},
  "brain": {"ms": 50.0, "wall_ms": 57.2, "spikes": 732,
            "mean_hz": 0.11, "clipped": false}
}
```

Округление в упаковке идёт по семантике DM (`round()` в DM округляет 0.5
вверх, в Python — к чётному). Это сторожит тест
`test_pack_is_one_char_per_cell`.

## Устройство движка

Событийно-управляемый LIF по CSR-матрице, разложенной по
**пресинаптическому** нейрону. На шаге:

1. отдать слот кольцевого буфера задержек в `g`, обнулить слот
2. затухание `g *= exp(-dt/tau_s)`, добавить пуассоновский вход
3. мембрана: `v += (v_rest - v + g - inhib) · dt/tau_m`, рефрактерных держим на `v_reset`
4. спайки `v > v_th`, сброс `v = v_reset`, `g = 0`, рефрактерность
5. разноска: для спайкнувших собирается плоский диапазон их рёбер и
   `bincount` кладёт веса в слот `(текущий + n_delay)`

Стоимость шага — `O(n)` на плотные векторы плюс `O(спайки · исходящая
степень)`. Умножения на всю матрицу не происходит: при типичных единицах
герц спайкует несколько десятков нейронов за шаг, и это на порядки дешевле,
чем 14 миллионов операций разреженного matvec.

Матрица связей общая на всех мух в процессе (read-only), индивидуальны
только `v`, `g`, рефрактерность и буфер задержек — около 2 МБ на особь.

Есть второй бэкенд на torch с `index_add_`; на CPU он не быстрее numpy,
поэтому `backend: auto` выбирает torch только под CUDA.

Переопределений процедур ядра модуль не делает: единственная добавка к
существующему типу — `/turf/proc/on_fire_check()`, новая процедура.
Столкновения ловятся не через `Bump()`, а по факту неудавшегося шага,
именно чтобы не переопределять ядро.

Всё равно прогоните `dreamchecker` перед первой сборкой — он ловит то,
что чтением исходников не поймаешь.
